## Read First — the load-bearing block
- **What exists now:** four JavaScript params of MCP tools (`EMBEDDED_CODE` — `evaluate_script.function`, `navigate_page.initScript`, `browser_evaluate.function`, `browser_run_code_unsafe.code`, matched on the tool-name suffix of `mcp-<server>-<tool>`) are `param_mode == "embedded"`: a bare `${…}`, an Issue and `$${` are sent verbatim; only `${x|json}` (a **JSON insert**) is pflow's, and it enters as a JSON/JS literal (`to_json`). `|json` anywhere else is a validation ERROR and is kept verbatim at run time.
- **Read these first:** `core/workflow/template_surfaces.py` (`ParamMode`, `EMBEDDED_CODE`, `param_mode`, `TemplateSurface.mode`); `core/templates.py` (`_JSON_INSERT`, `Expression.as_json` / `bare_raw`, `embedded_code`, `hidden_inserts`, `balanced_template`, `near_miss_insert`, `resolve(…, embedded=)`, `_resolve_string`, `to_json`); `core/workflow/data_flow.py` (the "Embedded code" section: `embedded_references`, `_validate_embedded_code`, `template_reads`, `ScopeKind`/`StepScope.kind`); `runtime/template_validation/validator.py::_validate_malformed_templates` (misplaced / hidden / near-miss inserts); `runtime/engine/template_resolution.py` (`split_params`, `resolve_templates`); web `graph/scan.ts::templateTokens`, `utils/format.ts::parseTemplate`.
- **Invariants that must NOT break:**
  1. **Embedded code is ONE policy view over ONE parse** (`embedded_code(parse(text))`) — every reader (validator surfaces, runtime, graph edges, canvas, web `templateTokens(…, "embedded")`) consumes that view; never a second tokenizer. A reader that walks raw `parse()` on an embedded param brings back phantom edges/chips/Pass-6 checks/env expansion for JavaScript's own `${a + b}`. Guard: `test_embedded_code_consumers.py` (one row per consumer, mutation-verified).
  2. **`split_params` decides `"embedded"` with `has_templates(value, embedded=True)`** — an embedded param with no insert is STATIC, so `$${` reaches the tool as `$${` (in JS: a dollar sign then an interpolation). Routing it through ordinary `has_templates` collapses the escape and drops the `$`.
  3. **A JSON insert is never `is_simple`** (`Template.is_simple` checks `as_json`). If it were, the engine's container auto-parse would turn the JSON text back into a dict and the tool would receive Python's repr.
  4. **`Expression.raw` includes the `|json` suffix** (reassembly invariant `source[span] == "${" + raw + "}"`, `## Cache` chunk names, plan printing). Code that needs the expression without it uses `Expression.bare_raw` — the one home of that stripping (binding fixes, §5 fix line, runtime `classify_unresolved_references`).
  5. **The embedded-code report (§4a ERROR, §4b/§4c/§4d WARNINGs) lives in `validate_data_flow`, which the compiler also runs** — same rule as Task 118's invariant 6. Moving it back into the template validator re-opens the falsifier's W1: a dynamic child (`workflow: ${…}` → `_validate_and_compile_child`, compile only) silently sends a stale `'${input}'` as literal text and exits 0.
  6. **"Is this input used?" has one answer, `data_flow.template_reads`** (inserts only, for embedded params; output sources as the runtime reads them; cache vars; carry index sources; body-leftover roots). The unused-input check and the §4a ERROR both read it — a second union diverges and either double-reports or silences the bug ("one mistake, one diagnostic").
  7. **`|json` is a fixed WORD, not a filter position.** In JavaScript `${flags|mask}` is legal code; each word pflow claims is taken from that language, so a general `|<name>` grammar would silently change existing JS.
  8. **The web never decides the mode** — Python sets `RFParam.mode`; every TS reader passes `param.mode` to `templateTokens`/`parseTemplate`. No TS copy of `EMBEDDED_CODE` (118's `isCodeBody` mirror was deleted).

## Patterns & Anti-Patterns
- **A param's template mode is ONE classification (`param_mode`) consulted by name.** Callers compare `!= "body"` / `== "embedded"`; adding a mode means auditing every caller of `param_mode`/`template_params`. Adding a tool to `EMBEDDED_CODE` silently flips every existing bare `${x}` in that param from resolved to sent — the §4a/§4b diagnostics are the required safety net, not decoration.
- **Policy over one parse result.** New "how pflow reads this text" behaviour goes into a view over `parse()` (spans preserved), never a second tokenization (`embedded_code`, web `templateTokens` modes).
- **Report where the compiler also runs** (data flow) for anything whose absence makes a run silently wrong; the template validator is skipped on dynamic children.
- **Structured provenance, not string rewriting:** carry `as_json` on the operand and render through one primitive (`written_reference`) — the rewrite version needed a workflow-wide "insert-only" guess and still missed changed-path suggestions.
- **Apply-the-fix tests:** every suggested fix is pasted back and re-validated (W2 was found exactly this way — a binding fix that validation rejected).
- **Anti-patterns rejected:** a schema heuristic or author marker for "is this code" (switches typo detection off on non-code / new grammar); "tolerate every non-pflow `${…}`" (scope-dependent meaning — a JS `${item.id}` inside a batch silently replaced); honouring `|json` at run time everywhere (a compile-only run would execute what validation rejects); a general `|<filter>` position (invariant 7); a TS copy of the table.

## Gotchas & Non-Obvious Coupling
- **A module-scoped pytest fixture runs BEFORE the function-scoped autouse `isolate_pflow_config`.** `tests/shared/mcp_tool.register_mcp_tool` writes the MCP config and registry; called from a module-scoped fixture it overwrote the user's REAL `~/.pflow` (`chrome-devtools` → `{"command": "true"}`, a stub `evaluate_script` with no `pageId`) on every `make test` until fixed — breaking every screenshot workflow and any sibling worktree's chrome-devtools runs. Anything that touches pflow config must be function-scoped.
- **`hidden_inserts` must scan every `${` opening (overlapping)** — `finditer` consumed `` `${"${x|json}"}` ``'s inner insert. And an Issue ends at its first `}`, so near-miss detection reads `balanced_template` (quote-aware) — `${{}|JSON}`, `${title ?? "}"|JSON}`.
- **Pass 5 de-duplicates by message at display:** two consumers of one missing producer path (one bare, one insert) collapse to the first suggestion on the CLI; the structured diagnostics are each right. Pass 8 names the consumer, so both show.
- **`StepScope.names` maps name → `ScopeKind`** (changed from prose in the gate); `owner()` renders prose from one table. Task 118's body diagnostics are byte-identical.
- **`unresolved_references[]` gains `"as_json": true` only when true** (additive in CLI/MCP JSON).
- **The web renders a dict param as JSON; ref segments carry parsed `operands`** — inside JSON a ref's shown body (`up.stdout ?? \"fallback\"`) is not its parseable body. Dict params are never teal (shiki owns `lang: json`, as on main); the selected-edge mark is what W1 restored. `CodeBlock.code` / `ResolvedBatchItem.value` are now `unknown` (values, not text).
- **A converted workflow's content hash changes** → a paused/failed run resumes only with `pflow resume --force`; a converted step moves static → template params (one memo-cache miss).
- **`registry_run` (MCP single-node run) rejects any param containing `eval(`** (#722, open) — the §4c `eval(${gen.code|json})` form works in workflow runs, not there; the guide says so.

## Breaking changes (no external users; all ruled or logged)
- A saved workflow with a bare `'${x}'` in an embedded param (the old taught form) now fails validation with §4a and its fix — including dynamic children (at compile).
- A workflow that wrote `$${…}` in JavaScript (as the old docs taught) now sends `$` + a JS interpolation — **no diagnostic**. No in-tree workflow does this.
- Web: an Issue (`${ x }`, `${a + b}`) in an ordinary Template param is no longer a chip/teal/substitution anywhere; `$${x}` is literal everywhere (#683's three escape-blind copies).

## Known limits / follow-ups (verified, not built)
- `${[1, "a"]|json}`, `${title|json|json}`, `${row["full name"]|json}` in embedded code pass validation and fail loud at the tool (outside R4's ruled scope; would need unruled text).
- `pflow report` reads a failed embedded param with the ordinary view (can suggest for a bare JS `${step.missing}`) — the trace carries the class name, not the IR type `param_mode` needs.
- MCP `registry_run` success never forwards validation warnings (pre-existing, 118's review).
- Python↔TS drift on non-ASCII identifier/whitespace classes (`\w`/`\s`); a committed Python↔TS differential (485 sources, 0 diffs, executed in scratch) is a follow-up alongside Task 170's.
- #683's second clause (batch preview shows `true`/`null` where sh receives `True`/empty) — not D10's.
- `examples/nodes/agent/claude-schema.pflow.md:93` writes `$${review…}` meaning "$ + value" (pre-existing).
- Screenshot skill: no DOM-text reader workflow (two phases hand-wrote one); `pflow mcp describe` mis-splits a hyphenated server name (`Server: chrome`); #722 (`eval(` in `registry_run`).
- An insert inside a longer template literal (`` `Hello ${name|json}` ``) is not detected as "inside quotes"; integers above 2^53 lose precision in JavaScript.
